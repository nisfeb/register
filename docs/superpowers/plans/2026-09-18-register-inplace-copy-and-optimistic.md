# Register: copy edited in place, and an optimistic UI

Two changes sneagan asked for on 2026-09-18 after using the backoffice: "an admin should be able to edit copy in place rather than this hideous copy page. the email content can't really be edited in place but everything that can should be. also the UI feels slow. have it optimistically show and show a spinner if you have to." One implementer, one review, one fix pass. Recipes for `~wex` in `2026-09-17-register-phase-1.md` lines 30 to 95; the wex loom note: a `|commit` that bails `meme` needs one `|meld`, and commits can take 12 minutes after it.

## 1. Copy in place, on the pilgrim's page

- `GET /api/status` gains `owner: true` when eyre's `authenticated` flag holds and src is our (the same test as `own`), else false (or absent). Nothing else about status changes for a stranger.
- `PATCH` is not in the route table; use `POST /api/admin/copy/set` with `{"key": "...", "value": "..."}` (owner, behind `act`): a new writer op `set-copy-key` that reads copy.json, refuses an unknown key (400 `key: not in copy`), refuses a value over 4000 bytes, writes the merged document, notes the ring with the key in `why`. One key per call. The whole-document `PUT /api/admin/copy` stays.
- `public.js`: when `status.owner`, the header shows a small "Edit text" toggle (a button, `#edit-copy`), off by default, remembered in `localStorage['register.editcopy']`. When on:
  - `body` gets class `editing`; `t(key, vars)` renders the RAW template with its `{{placeholders}}` visible (so "{{percent}}% full" reads literally), wrapped as `<span class="copy" data-copy="<key>" contenteditable="plaintext-only" spellcheck="true">…</span>` (escaped). Every `t()` call site that lands in innerHTML goes through one helper `tx(key, vars)` that does the wrapping in edit mode and plain `esc(t(...))` otherwise, so no call site is special. Attribute values (placeholders, `value=`, `title=`) are not editable in place; that is fine.
  - In edit mode, clicks on `.btn`, links and `[data-act]` do nothing (the handler returns early; `a.btn` gets `preventDefault`), inputs are `readonly`, and the form does not autosave. The pilgrim flow is frozen; only text is live.
  - On `blur` of a `.copy` span whose text changed: POST `/api/admin/copy/set` with the `x-actor` header (the same actor prompt as the backoffice, key `register.actor`; copy the small prompt into public.js), show a 300 ms tick beside the span on success or the error text in red; the local `status.copy[key]` is updated at once so a re-render keeps the new text (optimistic). Enter in a span blurs it (single-line strings) except for `landing.intro`, `form.assistance.help`, `next.*.body`, `manage.*` bodies and `stub.banner`, where Enter inserts a newline. A change to a key still rendering `{{x}}` placeholders the original had must keep every placeholder the original had: refuse locally with "keep {{x}}" in red and restore the text.
  - A "Show all steps" row appears under the toggle in edit mode: buttons Landing, Form (full), Form (Bambino), Waiver step, Payment step, Assistance, Wait list, Complete, Cancelled, Manage, Closed, Sold out. Each renders that view with a FAKE registration or status (a local fixture, no ship call) so every pilgrim-facing string is reachable without walking the flow. The fixture flags are obvious in the rendering (a "preview" ribbon).
- The backoffice's `#copy` view becomes **Emails**: only the `email.*` keys, grouped by template (subject and body side by side, the body a textarea with the placeholders listed under it), Save per template posting each changed key through `/api/admin/copy/set`. A one-line note at the top says every other string is edited on the public page with "Edit text". The nav label changes from Copy to Emails. The old whole-document editor is deleted.

## 2. Optimistic UI and spinners

Principle: the page shows the result of an action the moment the ship accepts the request, then reconciles with the ship after a short delay and on the beacon. Every wait a person can notice shows a spinner. Nothing waits for a read-after-write to paint.

- **A shared pattern in all three pages** (`admin.js`, `checkin.js`, `public.js`): a top progress bar (`#busy`, 3px, accent colour, `position: fixed`) that shows while any fetch is in flight (a counter, not a flag); buttons that trigger a fetch get `disabled` and a small inline spinner (`.spin`, a CSS border animation) until the fetch answers; a view that has no data yet shows a centred spinner with "Loading" instead of blank.
- **Backoffice** (`admin.js`): every action on a registration (promote, assist, pay, paper waiver, refund, exempt, reinstate, cancel, notes, edit, resend) applies its expected change to the in-memory registration and the roster row at once (status, payment, waiver, exempt, position 0, history line with `by` the actor and `at` now, marked `pending: true` so it renders with a faint style), renders, then re-fetches that registration after 1200 ms and again on the beacon; the pending mark clears when the fetched copy shows the change. A failed request rolls the optimistic change back and shows the error. Roster load: paint the cached roster from `localStorage['register.admin.roster']` first (with its age in the status line), then replace when the fetch answers. Reports: compute from the roster already in memory; never refetch just to open the tab. Settings and copy saves: optimistic with the spinner on Save.
- **Check-in** (`checkin.js`): already optimistic for taps; add the progress bar, the button spinner on "Check in everyone" and Save counts, and the Loading state on first open with no cache.
- **Pilgrim page** (`public.js`): Submit, Sign, Pay, Save and Cancel buttons show the spinner and disable while in flight; after submit the next-step page renders from the submit answer at once (status, position, fees are in it) instead of waiting for the retry loop, and the reg fetch reconciles in the background; the landing shows a Loading spinner until status arrives.
- **Nexus**: `GET /api/admin/reg/<rid>` and the pilgrim's `GET /api/reg` are fine. `GET /api/admin/regs` loads every registration; keep it but make sure it is called once per view change, not per keystroke or per action (the page keeps the roster and patches rows). No indexing work in this pass; sneagan said speed itself is a later discussion.

## 3. Proof

- Gate: `POST /api/admin/copy/set` with an unknown key is 400, with a known key changes `/api/status`'s copy, without `x-actor` is 400, without the cookie 403; `status.owner` is true with the cookie and false without.
- Node test additions where the helpers are pure: the placeholder-keeping rule; the optimistic row patch and rollback in admin.js (export the helpers as checkin.js does).
- Click-throughs: `scripts/admin-click.js` gains: an action shows the pending style at once and the plain style after reconcile; `scripts/checkin-click.js` unchanged; a new `scripts/public-edit-click.js`: with the cookie, toggle Edit text, change `landing.full.title` in place, blur, see the tick, reload, see the new text; the Show all steps buttons each render without an error; a change that drops a placeholder is refused locally.

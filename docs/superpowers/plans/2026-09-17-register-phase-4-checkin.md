# Register Phase 4: check-in and the day's counts

**Goal:** the volunteers' app at `/apps/register/checkin`: an installable PWA that caches the roster, checks people in by tap with a green or red wristband answer, queues taps offline and posts them when the phone is back, and takes the actual counts per activity per day. Spec section 5 is the requirement; this plan is the brief. Phase 3 (the backoffice) is done before this; build on its head. Phase 2 (providers) is deferred by sneagan; nothing here depends on it.

**Working rules:** one implementer, one review at the end. Recipes for `~wex` in `2026-09-17-register-phase-1.md` lines 30 to 95. That plan's Global Constraints hold. Gate in the foreground only. Never touch `~ricsul-bilwyt`.

## 1. Library (`code/lib/register.hoon`, tests)

- `+checkin-day |=(t=@t (unit @tas))`: `fri`, `sat`, `sun` to `%fri`, `%sat`, `%sun`, else `~`.
- `+with-checkin |=([r=reg i=@ud day=@tas by=@t now=@da undo=?] (unit reg))`: `~` when `i` is past the party; sets or removes `checkins.(snag i people.r)` at `day` (`[now by]`); `+note-hist` `'checked in <first last> <day>'` or `'undid check-in <first last> <day>'`. Idempotent: setting an existing check-in keeps the earlier `at` and adds no history line; removing a missing one is a no-op. Tests: set, set again (unchanged), undo, undo again (unchanged), bad index `~`.
- `+wristband |=(r=reg (each ~ @t))`: `[%& ~]` when status is `%complete` and `waiver.status` is `%completed` (or the waiver method is `%paper`), else `[%| why]` with why one of `'unpaid'` (status `%payment`), `'awaiting assistance decision'`, `'waiver not signed'`, `'on the wait list'`, `'cancelled'`, `'draft'`, `'not registered'`. Tests for each.
- `+en-roster-row |=([r=reg day=@tas] json)`: `rid`, `status`, `track`, `exempt`, `wristband` (`ok` and `why`), `people`: a list of `{i, first, last, child, walks (this day), bus, mass_fri (fri only), holy_hour (fri only), social (this day: social_fri on fri, social_sat on sat, none on sun), sun_ten (sun only), checked (bool), at, by}`. Only registrations that are active (not draft, not cancelled) are in the roster; cancelled ones are carried with `status` so a volunteer searching a name sees "cancelled" rather than nothing (include them, the page shows the red answer).
- `+planned |=([regs=(list reg) day=@tas] json)`: the planned counts for the day from counted people: `walk`, `mass` (fri), `holy_hour` (fri), `social`, `bus`, `sun_ten` and `sun_short` (sun), `checked` (people checked in that day). Test on a small fixture.

## 2. Nexus (`code/nex/register/app.hoon`), owner only

- `GET /checkin`, `/checkin.css`, `/checkin.js`, `/sw.js`, `/manifest.json`, `/icon-192.png`, `/icon-512.png` serve `code/nex/register/checkin.html`, `checkin.css`, `checkin.js`, `sw.js`, `manifest.json`, `icon-192.png`, `icon-512.png`. The manifest, the icons and `sw.js` are served WITHOUT the cookie (browsers fetch them uncredentialed; lattice does the same and says why in its route comments); the page and its script and style need the cookie, with the 302 to the login page for `/checkin` as the backoffice does. Icons: render two PNGs from `code/icon.svg` with `rsvg-convert` or `convert` if present, else a solid blue square PNG generated by a few lines of Python (zlib + struct); commit the bytes; load them with `/&` and serve with `image/png`, `cache-control: public, max-age=86400`. `sw.js` is served as `text/javascript` with `cache-control: no-cache` and `service-worker-allowed: /apps/register/`. `manifest.json` as `application/manifest+json`: name "BSC Check-in", `start_url` `/apps/register/checkin`, `scope` `/apps/register/`, `display` `standalone`, theme and background colors from the palette, the two icons. A `.json` name so clay has a mark for it (lattice's trap 17).
- `GET /api/checkin/roster?day=fri|sat|sun`: `{"day", "now", "rows": [en-roster-row...], "planned": {...}, "counts": <the day's object from counts.json>}`. Sorted by the first person's last name.
- `POST /api/checkin`: `{"day": "fri", "checkins": [{"rid", "i", "undo": false}, ...]}` up to 200 per batch; each item is a `checkin` writer op with `by` from `admin-by` (the volunteer's name); a bad rid or index is answered per item; the answer is `{"applied": n, "rejected": [{rid, i, why}]}`. The writer op `checkin {rid, i, day, undo, by}` applies `+with-checkin` and refuses cleanly on `~`.
- `GET` and `PUT /api/admin/counts` exist from phase 3; the check-in app uses them for the day's actuals with the same document shape.
- `+on-load`: the new files as `%over`.

## 3. The PWA (`code/nex/register/checkin.html`, `checkin.css`, `checkin.js`, `sw.js`, `manifest.json`)

Large type, big tap targets, one column, built for a phone in sunlight: high contrast, `--ink` on white, buttons at least 48px tall.

- **Header:** "Check-in", a day selector (Fri, Sat, Sun) defaulting to today when today is one of the event days (settings.event.days from `/api/status`) else Fri, the "acting as Susan" name (same localStorage key `register.actor` as the backoffice; prompt on first tap; the header shows it always since every tap is signed by it), a sync badge: green "synced", amber "3 waiting" (queued taps), grey "offline".
- **Roster:** fetched on open and every 60 seconds when online; stored in `localStorage['register.roster.<day>']` with its fetch time; on open, the stored roster paints first and the fetch replaces it. A search box (last name, first name, email not shown but matched, rid); typing filters as you type. Each party is a card: the party's names with the checked ones ticked, the wristband answer as a colored bar on the card's left edge (green ok, red with the why), and one big button per person: "Check in" (tap) or "Checked in 7:42 by Sarah" (tap again asks "Undo?" inline). A party-level "Check in everyone" button when more than one person. Below the name, small tags for the day: walk, bus, Mass, Holy Hour, social, 10 mi or 2.5 mi.
- **Wristband rule on tap:** green answer: the button turns green and shows "Wristband". Red: the check-in is still recorded (the volunteer decided) but the card shows the red why and "No wristband: unpaid" in the button.
- **Queue:** every tap appends `{rid, i, day, undo, at}` to `localStorage['register.queue']` and updates the local roster copy at once. A drain runs on tap, on `online`, on open, and every 15 seconds: POSTs the whole queue in one batch, removes the applied items, keeps the rejected ones with their why shown on the card (a rejected item is rare: a rid that vanished). A 403 (the cookie expired) shows a banner "Log in again" with a link to `/~/login?redirect=/apps/register/checkin` and stops draining until the next open.
- **Counts:** a second tab "Counts" for the day: a grid of the day's activities (walk, Mass, Holy Hour, social, bus; Sunday adds the 10-mile and 2.5-mile starts) with three fields each: planned (read-only from the roster), actual (number), time (text), and a note; Save PUTs `/api/admin/counts` with only this day's object merged into the fetched document. Also works offline: a saved counts object queues in `localStorage['register.counts.<day>']` and PUTs on drain.
- **Live:** the beacon stream refreshes the roster (orrery's `stream()` copied); the roster refresh never wipes a card the volunteer is mid-tap on (apply the fetched rows, then re-apply the queued items on top).
- **`sw.js`:** caches the shell (`/apps/register/checkin`, `checkin.css`, `checkin.js`, `manifest.json`, the icons) on install with a versioned cache name; serves the shell cache-first; never caches `/api/`; on activate deletes older caches. The page registers it with `navigator.serviceWorker.register('/apps/register/sw.js', {scope: '/apps/register/'})`.

## 4. Backoffice touches (`admin.js`)

The reports view gains "checked in" per day beside planned and actual, and the roster gets a "check-ins" column (Fri/Sat/Sun ticks). The registration detail shows each person's check-ins with at and by, and an organizer can undo one (posts to `/api/checkin` with `undo`).

## 5. Gate, tests and a node test

`scripts/api-matrix.py` gains: `GET /api/checkin/roster?day=fri` 403 without the cookie, 200 with, rows sorted by last name, a complete party's `wristband.ok` true, a wait-listed one's false with `'on the wait list'`; `POST /api/checkin` with two items answers `applied 2`, a repeat answers `applied 2` with no new history line (idempotent), an undo removes it, a bad index is rejected by name; the roster shows `checked` true after the tap; `planned.walk` equals the count of counted walkers that day. Page smoke: `/apps/register/manifest.json`, `/sw.js` and the icons answer 200 WITHOUT a cookie with the right types; `/checkin` without a cookie is a 302.

`scripts/checkin-test.js` (node, no browser): loads `checkin.js` with a fake `localStorage`, `fetch` and `document` shim (the page's pure helpers are exported when `module.exports` exists, the way orrery's page does): the queue append, the drain removing applied items and keeping rejected ones, the roster merge that re-applies queued taps, the wristband text for each why, the day default from event days. `node scripts/checkin-test.js` prints ok lines and exits 1 on a failure.

A headless click-through with puppeteer-core (cookie set on the page): open `/apps/register/checkin`, set the actor, search a name, tap check-in, see the green button; set the page offline (`page.setOfflineMode(true)`), tap another, see "1 waiting", set online, see "synced" and the roster row `checked` true through the API.
